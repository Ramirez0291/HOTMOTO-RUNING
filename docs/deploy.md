# デプロイ

## Docker を使う（おすすめ）

Docker（Compose 付き）が入ったマシンが必要です。クラウドのサーバーなら、イメージのビルドに使うので 2 コア・4 GB メモリ以上をおすすめします。

```bash
git clone <あなたのリポジトリ> nirinhot
cd nirinhot
node scripts/init-env.ts --llm-key <モデルの API キー>
```

`init-env.ts` は `.env` を作り、ランダムな鍵と管理者パスワードを入れ、パスワードを 1 回だけ表示します。マシンに Node がなければ、`.env.example` を `.env` にコピーし、`ADMIN_PASSWORD`（12 文字以上）、`SESSION_SECRET`、`IMG_PROXY_SIGN_SECRET`、`POSTGRES_PASSWORD`（それぞれ `openssl rand -hex 32` で作る）と `LLM_API_KEY` を自分で入れます。

起動前に `.env` の `SITE_URL` を確認します：ローカルで試すなら `http://localhost:3000` のままにし、サーバーにデプロイするなら読者が実際にアクセスするアドレスに変えます。たとえばサーバーの IP でアクセスするなら（例の IP を自分のものに替える）：

```dotenv
SITE_URL=http://192.0.2.10:3000
```

RSS、シェアのリンク、サイトマップ、Agent 向け Markdown の絶対リンクはすべてこの値を使い、ブラウザでアクセスしたアドレスに合わせて変わることはありません。ドメインと HTTPS を使うときは下の「ドメインと HTTPS」に従って設定します。

設定が終わったら起動します：

```bash
docker compose up -d --build
```

起動したら `http://サーバーのアドレス:3000` を開きます。管理画面は `/admin` で、管理者パスワードでログインします。初回起動時に示範の情報源を取り込み、1〜2 分で内容が出始めます。初回に取り込む資料（示範の情報源では各 8 件まで）はおよそ 30 分で処理が終わります（1 件ずつ予備選別、採点、構造化、タイトルと要約の執筆、まとめを行う）。

`docker compose` は 5 つのコンテナを起動します：`db`（PostgreSQL 17）、`setup`（起動のたびにまずデータベースのマイグレーションとシードを実行して終了）、`api`、`worker`（取得、モデルの処理、定期作業）、`web`（ウェブ）。`web` が受け取るのはサイトのアドレス、API のアドレスなどウェブの設定だけで、HTTP で API を読みます。データベース、モデル、管理者の鍵、データのボリュームはバックエンドのコンテナにだけ渡します。

コンテナの時刻は UTC のままでかまいません。日報の締めや画面の日付は、サイトの設定 `site/site.ts` の `TIME_ZONE`（いまは日本時間）で計算します。

### ドメインと HTTPS

まずドメインをサーバーに向け、`.env` で次を設定します：

```bash
SITE_URL=https://example.com
SITE_DOMAIN=example.com
PORT=127.0.0.1:3000        # 3000 番ポートはローカルの Caddy 専用にし、直接は公開しない
TRUST_PROXY=true           # 訪問者のアドレスを Caddy が転送するリクエストヘッダーから読む
```

それから HTTPS 付きで起動すると、Caddy が証明書を自動で取得・更新します：

```bash
docker compose --profile https up -d --build
```

すでに Nginx があるなら Caddy は使わず、サイトを `http://127.0.0.1:3000` にリバースプロキシし、`proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` を付け、`.env` で `TRUST_PROXY=true` にします。`SITE_URL` は必ず読者が実際にアクセスするアドレスにしてください：生成するリンク、RSS、シェア画像、MCP がこれを使います。

MCP は既定で `SITE_URL` のホストと `localhost`、`127.0.0.1`、`[::1]` を受け付けます。ほかのホストは `MCP_ALLOWED_HOSTS` にカンマ区切りで設定します。例：`extra.example:8443,[2001:db8::1]`。ホスト名は大文字と小文字を区別せず、IPv6 は角かっこが必要です。0〜65535 の 10 進のポートを付けられ、照合ではポートを無視します。パス、ユーザー情報、不正なポートを含む設定は効きません。`127.1` のような別名は明示的に挙げる必要があります。この設定は Host の検査だけに影響し、ブラウザの Origin の許可は広げません。

### 海外の情報源と送信プロキシ

海外の情報源が取れないときは、`.env` に `EGRESS_PROXY_URL` を設定します：情報源と画像の取得はこのプロキシを通り、モデルのインターフェースの呼び出しは通りません。

### 更新

まず下の節に従ってデータベースをバックアップします。ビルドが終わったら古いサービスを止め、マイグレーションと新しい版のサービスを実行します：

```bash
git pull
docker compose build
docker compose stop api worker web
docker compose run --rm setup && docker compose up -d
```

マイグレーションが成功してからサービスを起動します。マイグレーションが失敗したら、まずエラーを確認し、起動を続けないでください。HTTPS の設定のサイトは `--profile https` を付けたままにします。古い API と worker はマイグレーションの前に止める必要があります：マイグレーションはテーブルや列を消すことがあり、古いコードが動いたままだとエラーになります。worker を正常に止めると、進行中の有料の呼び出しの終わりを待ちます（最長 3 分余り）。Docker を使わないデプロイでも「バックアップ、ビルド、API/worker/web の停止、マイグレーション（`scripts/migrate.ts`）、シード（`scripts/seed.ts`）、起動」の順で更新します。

新しいマイグレーションが長くロックを待つと、ファイル名と待ちのタイムアウトを報告します。先にロックを持っているトランザクションを処理してから setup を実行し直し、マイグレーションを飛ばしたり記録を書き換えたりしないでください。並列のインデックス作成が中断すると無効なインデックスが残ることがあります：エラーの対象を確かめてから、`DROP INDEX CONCURRENTLY <インデックス名>` でその失敗したインデックスを消して実行し直します。有効だが定義の違う同名のインデックスは、先に違いを確認してください。

#### 二輪・日本語版への作り直し（2026 年 10 月 4 日）

AIHOT の示範（AI 業界・中国語）から、二輪市場・日本語のサイト NIRINHOT に作り直しました。公開インターフェースのバージョンは 4.0.0 のままです。新しく立ち上げるサイトなら、特別な作業は要りません。示範の設定ですでに動かしていたデータベースを引き継ぐ場合は、次に注意してください。

- **時刻の基準が北京時間から日本時間に変わりました**（`site/site.ts` の `TIME_ZONE`）。日報の締め（毎日 08:00）、週報・月報の期間、画面の日付、定期作業がすべて 1 時間早く（日本時間で）動きます。既刊のレポートは書き直しません。
- **モデルが書く言語が日本語になりました**（`SITE.language`）。サイト内の翻訳は `translations.lang = 'ja'` で保存し、以前に `'zh'` で保存した中国語の翻訳は読まれなくなります（データは消えません。要らなければ削除してかまいません）。日本語の原文は翻訳しません。
- **カテゴリが変わりました**（`new-models`、`market`、`policy`、`industry`、`gear`、`motorsports`、`events`、`review`、`opinion`）。古いカテゴリの key（`ai-models` など）が付いた既存の記事は、どのカテゴリの絞り込みにも出ません。示範のデータを引き継ぐより、データベースを作り直すことをおすすめします。
- **示範の情報源が二輪の 18 件に替わりました**。初回起動時に取り込むだけで、既存の情報源は上書きも削除もしません。古い AI の情報源は管理画面で停止してください。
- **シェア画像のフォントが Noto Sans JP になりました**（`assets/og-fonts/`）。テンプレートのバージョンを上げたので、シェア画像は描き直されます。
- **モデルとのやり取りの項目名が変わりました**：内容理解の JSON は `title`・`summary`、タイトルと要約のプロンプトの行は `title:`・`summary:`・`body:` です。プロンプトの内容が変わったので、以前の受領記録は再利用されず、新しい資料から新しい版で判断します。

#### 公開の出口の訂正、取り下げ、キャッシュ（2026 年 10 月 4 日、元の AIHOT）

公開インターフェースのバージョンは 4.0.0 のままで、環境変数やサイトの設定の追加は要りません。マイグレーション `0056`、`0057` は公開の一覧の検索の統計を作って集めるだけで、データを消したり既存の内容を書き換えたりしません。

- **過去のレポートも再検証が必要**：日付、週、月が決めるのはどの号かであって、内容が永久に変わらないことではありません。レポートは発行時に書いたタイトルと要約を保ち、情報源の名前と引用の日時はいまの公開資料に従います。取り下げた引用と、それに依存する導入文やカバーはもう配りません。レポートの複製を持つクライアントは、`Cache-Control` が切れたら `If-None-Match` を付けて取り直します。
- **Nginx や CDN のキャッシュを自分で設定したサイトは規則を確認**：公開のウェブページ、ナビゲーションのデータ、API、RSS、記事の Markdown、レポートのシェア画像、サイトマップは、アプリが返すキャッシュの期限に従います。より長い期限を加えたり、期限切れの後にオフラインで古い内容を返したり、古いレスポンスを転送するときに寿命を計り直したりしないでください。プロキシと CDN で動的な内容を重ねてキャッシュすることを避け、更新時にはこれらのパスの既存のキャッシュ（接続の説明 `/api/v1/agent` と `/openapi-v1.json` を含む）を消してください。
- **サイトマップの作り直しに失敗しても古いファイルを使い続けない**：プロセス、ディスクの複製、HTTP のレスポンスは元の 5 分の期限を共有し、期限切れで作り直せないときは `503` と `Retry-After` を返します。

#### コミュニティの修正と新しい資料の日時の規則（2026 年 10 月 4 日、元の AIHOT）

- **初回の取り込みの後は情報源の保管庫を収めない**：その後の取得では、情報源を加える 48 時間前より後に公開された項目だけを収めます（[情報源](sources.md) の「古い記事で埋めない」）。
- **信頼できる発表日時のない新しい資料はまず公開しない**：元の情報源か原文のページから日付を読んでから新旧を判断します。日付が不明な間は、記事のページ、構造化データ、Agent 向け Markdown は「収録日時」と書き、RSS は `pubDate` を書きません。
- **推論モデルの枠は明示の設定に**：既定のモデルは `LLM_REASONING_TOKENS`、名前付きのモデルは `site/models.ts` の `reasoningTokens`。
- **タイムゾーンのない時刻**（例：`2026-09-30 17:43:58`）は情報源の `publishedAtUtcOffset` で読み、既定はサイトの `TIME_ZONE` です。
- **マイグレーションで読み書きを止めない**：新しいマイグレーションは 1 つのファイルにオンラインで実行してよい文を 1 つだけ入れます。規則は [アーキテクチャ](architecture.md#データベースのマイグレーション) を参照。

それより前の元の AIHOT の更新（公開インターフェース 3.0.0・4.0.0 への更新など）は、元のリポジトリの `docs/deploy.md` を参照してください。このサイトはそれらより後の版から作り直したので、対応は要りません。

### 管理者のセッションと設定の変更

セッションの結び付けのマイグレーションは `0041` です。セッションはログインの方法、ログイン時の管理者の認証情報、飛書の身元に結び付きます。管理者パスワード、飛書の管理者の一覧、セッションの鍵を変えたら、すべての API プロセスを再起動して同じ新しい設定を読み込ませてください。設定ファイルを編集しただけでは、動いているプロセスに効いたことにはなりません。

有効な設定が変わると、パスワードのセッションは古いパスワードでの許可を受け付けなくなり、飛書のセッションはログイン時に取得した union ID かメールでいまの一覧を確認します（どちらか一方がまだ許可されていればよい）。飛書のログインアプリを止めるかアプリ ID を替えると飛書のセッションは無効になり、同じアプリの secret を替えるだけなら、まだ許可されている飛書のセッションはログアウトしません。SESSION_SECRET を替えるか消すと、両方のセッションが無効になります。

### バックアップ

`.env` に `DB_BACKUP_STORE_*`（S3 互換のオブジェクトストレージなら何でもよい）を設定すると、毎日 04:10 に自動でそこへバックアップします。1 回の完全なバックアップには、同じタイムスタンプのデータベースの `.dump` とファイルの `aihot-files-*.tar.gz` が含まれます：ファイルの包みには `uploads/` と、まだローカルにある `feedback-screenshots/` を入れ、画像のキャッシュやローカルのバックアップのディレクトリは含めません。

復元するときはこの 2 つを一緒に取り戻します：データベースのバージョンと互換の `pg_restore` で `.dump` を空のデータベースに復元し、ファイルの包みをデータディレクトリのルート（Docker では `/data`、Docker 以外では `AIHOT_DATA_DIR`、既定は `.data`）に展開し、包みの中のサブディレクトリの構造を保ち、動いているプロセスがそれらのファイルを読めるようにします。

下の手動の書き出しはデータベースだけで、上の添付のディレクトリは含みません：

```bash
docker compose exec -T db pg_dump -U aihot aihot | gzip > nirinhot-$(date +%F).sql.gz
```

データはすべて 3 つの Docker ボリュームにあります：`db`（データベース）、`data`（アップロードした画像、画像のキャッシュ、ローカルのバックアップ）、`caddy`（証明書）。`docker compose down` では消えませんが、`docker compose down -v` では消えます。

### ログを見る

```bash
docker compose logs -f --tail 100 api worker web
```

管理画面の「実行」ページで各定期作業の最近の結果を、「情報源」ページで各情報源の取得の状況を見られます。

## 費用の目安

- **モデル**：新しい資料はまず 1 回予備選別し、通ったものは 2 回採点し、1 回構造化し、1 回タイトルと要約を書き、それからまとめます（近い報道があるときだけ呼び出す）。ほかに出来事のまとめ文、週報・月報の総括、厳選の全文翻訳があります。日報はルールで編み、モデルを呼びません。元の AIHOT の示範の情報源での試しでは、初回に取り込んだ 152 件の資料でモデルの呼び出しはおよそ 930 回でした。その後の毎日の量は、情報源が毎日何件更新されるかによります。管理画面の「モデルと評価」ページで、各工程の呼び出し回数と入出力の token 数を見られます。
- **有料の収集**（X、WeChat、Jina）：リクエストごとの課金で、既定では使わず、鍵を入れたときだけ使います。
- 有料のサービスにはすべて 1 分・1 時間・1 日の呼び出しの上限があり（管理画面の「設定 → 有料リクエストの上限」）、超えると止まるので、一晩で請求が膨らむことはありません。0 にするとそのサービスをすぐに停止します。

## Docker を使わない

Node.js 24.11 以上と PostgreSQL 16 か 17 が必要で、OS は Linux か macOS です。Windows では WSL2 の中で動かすか、上の Docker の方法を使ってください。

```bash
npm ci
node scripts/init-env.ts --llm-key <モデルの API キー>
createdb nirinhot
```

`.env` に次を加えます：

```bash
DATABASE_URL=postgres://ユーザー名@127.0.0.1:5432/nirinhot
API_BASE_URL=http://127.0.0.1:3001
```

それから：

```bash
node --env-file=.env scripts/migrate.ts
node --env-file=.env scripts/seed.ts
npm run build -w @aihot/web

node --env-file=.env apps/api/src/main.ts          # インターフェース、3001 番ポート
node --env-file=.env apps/worker/src/main.ts       # バックグラウンドの作業
cd apps/web && NODE_ENV=production node --env-file=../../.env server.ts   # ウェブ、3000 番ポート
```

3 つのプロセスは常に動かしておく必要があり、本番では systemd や pm2 で見守ります。worker を止めるときは少なくとも 210 秒与えてください（systemd の `TimeoutStopSec`、pm2 の `kill_timeout`）。進行中の有料の呼び出しを終わらせるためで、早く強制終了された呼び出しは結果不明になり、少なくとも 30 分後に自動で解放されてから再試行されます。

開発ではホットリロード付きの方法を使います：`npm run dev:api`、`npm run dev:worker`、`npm run dev:web`。開発中にログインなしで管理画面に入りたいときは、`.env` で `DEV_AUTH_ROLE=admin` にします（本番では起動を拒否します）。
