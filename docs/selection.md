# 厳選と校正

## 資料が厳選になるまで

1. **取り込み**：同じ URL、同じ内容は 1 つだけ残します。タイトルかフィードの要約しかないものは、先に原文のページを取得してから判断します。
2. **予備選別**（`prefilter.md`）：この業界の話かどうか。広めに入れ、明らかに無関係なものだけを止めます：`BLOCK` の資料はどの公開ページにも出ず、`PASS` と判断できない `UNKNOWN` は先に進みます。
3. **採点**（`selection-score.md`）：同じ採点基準で独立に 2 回採点します（0〜100）。**2 回の合計が 2 × しきい値以上**なら点数は足り、しきい値は情報源の格付けで違います。点数が足りたものも、6 番目の重複確認を通ってはじめて厳選に入ります。ページに出る点数は 2 回の平均（切り捨て）です。
4. **構造化**（`structure.md`）：採点と同時に行います。カテゴリとタグ（ページに出るのはこちら）、主体の企業を出し、この記事が具体的な 1 つのニュースか、複数のことを扱うまとめ記事か、材料が足りず判断できないかを決めます。具体的なニュースなら、その事実（誰が、何を、何に対して、いつ）と、原文の出典と前提条件を抜き出します。トピックページ、出来事のまとめ、日報はすべてこれに頼ります。
5. **タイトルと要約を書く**：構造化が終わってから書きます。入選したものと、もう少しで入選したもの（平均点が `understandFloor` より高い）は、`content-understanding.md` に従って日本語のタイトル、答えを先に書く要約、注目ポイントを書き、それ以外は `summarize-*.md` に従って短いタイトルと要約を書き、「すべてのニュース」に入れます。
6. **まとめと重複確認**（`group-*.md`）：異なる情報源が報じた同じことを 1 つの出来事にまとめ、出来事のページにはまとめ文（`story-digest.md`）があり、「話題」は出来事ごとに並びます。点数が足りた資料も、まとめが終わるまで厳選には入りません：モデルが同時に、それが厳選済みの報道と同じニュースか、厳選がまだ伝えていない具体的な情報があるかを判断します。
   - 同じニュースの複数の報道はどれも入選できます：ウェブでは 1 つの閲覧グループに折りたたみ、API、RSS、同期のインターフェースではニュース 1 つにつき 1 件だけ、代表記事が出ます（公式の一次情報を優先し、次に全文があるもの、点数の高いもの、早く出たもの）。
   - 同じニュースではないが新しい情報もないもの（すでに明らかになった装備を言い方を変えて紹介し直す、別の販売店で取り扱いを始めただけ、選ばれた要点を繰り返すだけのまとめ）は厳選に入らず、「すべてのニュース」に残ります。複数のことを扱うまとめ記事は単独の出来事にならず、それが触れる出来事に結び付くだけで、厳選がまだ扱っていない重要な内容があるときだけ入選します。材料が足りずどのニュースか確認できないものは厳選に入りません。
   - 確認されるまで資料は「すべてのニュース」にだけあり、どれだけ待っても自動では通りません。モデルの呼び出しが失敗したり答えが形式に合わなかったりすると、その資料はそこで止まります：10 分以上待つとアラートが出て、管理画面の「実行」ページに一覧され、内容のページで「まとめ直す」ことができます。そのため、まとめに使うモデルは形式どおりに安定して答えられる必要があります。
7. **日報、週報、月報**：
   - **日報**は毎日 08:00（日本時間）に出ます（発行時刻は `site/site.ts` の `EDITION_TIMES`。以下は既定値で書きます）。前日 08:00 から当日 08:00 までを収め、ルールで編み、モデルを呼びません。1 つの出来事につき 1 件で、最も多く報じられたニュースの中で最も権威のある記事を取り、同じ出来事のその日のほかの進展を下に並べ、複数のことを扱うまとめ記事はそれが触れる最も重要な出来事の下に結び付けます。直近 7 号で報じたものは再び出ません。報じた出来事に進展があっても、当事者自身の新しい動き（試乗記や論評のような `commentary` のカテゴリは除く）があるか、その進展を 4 件以上の情報源が報じたときだけ本文に入り、それ以外は速報に入ります。入選した報道がなくても、公式の元の投稿があり、独立した参加者がすでに 3 件以上いる出来事は補います（日報にだけ入り、厳選にも配信にも入りません）。重要度の順に並べ（入選した報道の最高点、その日に話題にした独立した参加者、公式の元の投稿の有無、続報は減点）、上位 12 件が本文に入り、同じ情報源は最大 2 件、その後に最大 10 件の 1 行の速報が続きます。1 件目がトップで、リードはその記事自身のタイトルと要約です。2〜4 件目が今日の注目です。
   - **週報**（毎週月曜 10:00）と**月報**（毎月 1 日 10:30）は、その週・その月の日報から編みます：日をまたぐ同じ出来事は 1 件と数え、日報での位置（トップ、注目、何日載ったか）、報道の広さ、点数で並べ、週報は上位 20 件、月報は上位 30 件を取り、日報の節に従って欄に分けます。モデル（`report-period.md`、`report-period-sections.md`）は総括と、3 件以上ある欄の一文の導入だけを書き、項目を増減しません。項目にない名前や数字（ラテン文字の名前、3 桁以上か小数点やパーセントのある数字、語彙の企業）を書いたら、その文は使いません：総括はひな形で作った一文に替え、欄には導入を置きません。業界の一般語（`taxonomy.ts` の `PLAIN_TERMS`）とサイト名はこの制限を受けません。
   - 厳選は 1 号にだけ入ります：その日時で数え、入選の確認がそれより遅いものは確認の日時で数えます。締め切りの後に確認されたものは次の号に入ります。
   - 30 分ごとに確認します：時刻になった号を 1 回出し、すでに出た号は書き直しません。停止で逃した号や失敗した号は、その後の確認で補います。期間内に収める項目がなければその号は出さず、以後 30 分ごとに試し、10 時になっても当日の日報がなければアラートが出ます。

各工程のプロンプトはすべて `industry/prompts/` にあり、プロンプトを変えるのにコードは変えません。プロンプトのバージョンはその内容のハッシュです：プロンプトを変えると、その後の新しい資料は新しい版で判断し、判断済みのものは計算し直しません。

## しきい値：`industry/selection.ts`

```ts
export const SELECTION = {
  thresholds: { T1: 60, T1_5: 65, T2: 76 },   // 2 回の採点の平均が少なくともこの数に達する必要がある
  understandFloor: 50,                        // 平均点がこれより高い未入選の資料も、入選と同じ書き方で書く
};
```

公式の一次情報源（T1）はしきい値が低め、メディアと個人（T2）は高めです：同じことなら、公式の原文を先に読む価値があるからです。しきい値のない格付け（`EXCLUDE_MP`）は厳選に参加しません。

この数値は hotmoto が AI 分野で使ってきたしきい値で、厳しめです：数件少なく選んでも、ノイズは厳選に入れないという考えです。**二輪の設定でもまだこの値のまま**なので、下の方法で必ず校正し直してください。

## 校正

### 1. サンプルを用意する

自分の情報源から 100〜200 件の資料を選び、1 件ずつ「選ぶ / 選ばない」とラベル付けし、`.data/gold.jsonl` に保存します（`.data/` は Git に入りません）。1 行に 1 件：

```json
{"caseId":"moto-001","material":{"title":"原題","originalTitle":null,"publishedAt":"2026-10-01T10:00:00+09:00","sourceName":"情報源の名前","bodyZh":null,"bodyOriginal":"本文……"},"sourceFacts":{"sourceKind":"rss","sourceTier":"T1","firstParty":true,"language":"ja"},"samplingContext":{"benchmarkSplit":"development","samplingStratum":"new-model"},"gold":{"decision":"select"}}
```

| 項目 | 説明 |
|---|---|
| `caseId` | 一意の番号 |
| `material` | タイトル、原題、発表日時、情報源の名前、本文（サイトの言語の本文は `bodyZh`、原文は `bodyOriginal`。どちらか 1 つでよい） |
| `sourceFacts` | 情報源の種類、格付け、一次情報か（本番では `T1` だけが一次情報。ラベル付けでも揃える）、言語。格付けでどのしきい値を使うかが決まる |
| `samplingContext` | 任意。`benchmarkSplit` で開発用と検証用を分け、`samplingStratum` は自分の分類（「新型車」「販売統計」「中古車の宣伝」など）で、どの種類で間違えたかを見る |
| `gold.decision` | `select` 選ぶ、`reject` 選ばない、`either` どちらでも（正解率に数えない） |

`industry/gold.example.jsonl` に 2 件の例があります。

いくつかの助言：

- **難しい例**を多く入れる：あと少しで選ぶべきもの、あと少しで選ぶべきでないもの。一目で分かるものを入れすぎると正解率が見かけだけ高くなります。
- 一部を**検証用**（`benchmarkSplit: "holdout"`）に分け、プロンプトの調整では開発用だけを見て、最後に検証用でもう一度確かめます。プロンプトがその問題だけを解けるように調整されてしまうのを防ぐためです。
- ラベルを付ける人は、できればこのサイトの読者か、その好みに近い人にします。
- 評価が動かすのは予備選別と 2 回の採点だけで、6 番目の重複確認は含みません：その資料自体を選ぶべきかでラベルを付け、同じことの別の記事をすでに選んだからといって「選ばない」にしないでください。

### 2. 評価を実行する

```bash
node --env-file=.env scripts/eval-selection.ts --gold .data/gold.jsonl --split development --label "採点基準の第 1 版"
```

各サンプルで予備選別と 2 回の採点を実行し、次を出力します：

- 正解率、適合率（選んだもののうち正しいものの割合）、再現率（選ぶべきもののうち選べたものの割合）。
- しきい値を 40 から 90 まで 2 点刻みで変えたときのそれぞれの結果。
- 判断を誤った項目。完全なレポートは `.data/eval/` に書き、管理画面の SelectBench にも取り込みます。

`--models` を渡さなければ、評価は本番のいまの「厳選の採点」モデルの設定（管理画面での切り替え、`SCORE_MODEL`、既定のモデル）に従います。`--models default,deepseek-flash` で複数のモデルを明示して比べられます。ほかによく使う引数：`--n 200` 最大何件取るか、`--split holdout` 検証用だけを実行。

同じ評価の中で、異なるサンプルがまったく同じ採点の入力になったときは、モデルの採点結果だけを共有し、各サンプルはそれぞれの予備選別の結果、情報源の格付けのしきい値、正解で独立に採点します。失敗した結果もその実行の中で共有し、並列の初回実行とキャッシュでの再実行で評価の範囲が変わらないようにします。繰り返し実行すると既存の受領記録を再利用します。レポートの token の使用量と平均の所要時間は、関係する受領記録のすべての試行を合計するので、解析に失敗した後の再試行も漏れません。キャッシュでの再実行で表示されるのはそれらの受領記録の累計の使用量で、今回新たにかかった費用ではありません。

### 3. 誤りを見て、基準を直し、もう一度実行する

管理画面の SelectBench で、判断を誤った資料とモデルの理由を 1 件ずつ見ます：

- 選ぶべきなのに選ばれなかったものは、たいてい採点基準でそれがなぜ重要かがはっきり書かれていません：`selection-score.md` の「普通に評価しなければならない価値」にその種類の価値を書き、例を挙げます。
- 選ぶべきでないのに選ばれたものは、たいていノイズを抑えられていません：「抑えなければならないノイズ」に書きます。
- 全体として甘いか厳しく、誤った項目の点数がどれもしきい値すれすれなら、`industry/selection.ts` のしきい値を調整します。

先に基準を直し、それからしきい値を動かします：しきい値は全体を動かすことしかできず、「どの種類で間違えたか」は解決できません。直すたびに実行し、SelectBench で各版を比べられます。

## モデルを替える

管理画面の「モデルと評価」ページで、各工程がいまどのモデルを使っているか、最近の成功率、所要時間、token の使用量を見られ、その場で切り替えられます（その後の新しい作業にだけ効きます）。採点のモデルを替える前に、`--models` で同じサンプルで比べてください。
